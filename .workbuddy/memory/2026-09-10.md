## exhentai 304 画廊自动下载队列（新功能）

**需求**：exhentai 列表页中归档状态为 304 (`NoNewerSeed`) 且 `!isNewer` 的画廊，自动加入下载队列串行执行，队列面板显示在页面左侧（复用现有卡片样式）。

**改动**
- `src/site/exhentai/exhentai-download-handler.ts`（改造）
  - 新增 `DownloadOutcomeKind` / `DownloadOutcome` 类型，把 `createHandler()` 闭包体抽成公开的 `async execute(): Promise<DownloadOutcome>`，`createHandler()` 退化为一行包装（手动点击语义不变）
  - 构造函数新增 `silent` 参数（默认 false），所有 `ElNotification` 收敛到 `private notify()`
  - 新增 `data-mansion-lock` 互斥属性，防止"队列自动执行"与"用户手动点击"同一画廊并发
  - `handleOutdatedTorrents` 返回值化（4 个出口）
- `src/store/download-queue-store.ts`（新增，146 行）
  - 模块级 `executor` 注册点（`setDownloadQueueExecutor`），不进 Pinia state，避免闭包被 reactive 包装
  - 串行 `drain()`：`busy` 在"执行 + 项间间隔"期间保持 true（`intervalMs=1500`），保证固定间隔且新入队不抢跑；失败继续下一项；`paused` 只阻止取下一项
  - 状态：`pending | running | success | skipped | failed`
- `src/site/exhentai/exhentai.ts`
  - `mount()` 注册 executor；新增 `private executeQueuedDownload()`：按 `#exhentai_gid_${gid}` 重新定位 DOM，`dayjs(item.dateMs)` 重建日期，`silent=true` 调用 `execute()`
  - 304 分支改为 `!isNewer && $download.length > 0` → `applyArchiveStyle` + 打标 `queueDownload`，**入队延迟到绑定完成后**（因为 `data-orig-href` 在绑定阶段才写入）
  - 修掉死判断 `if (!$download)` → `if (!$download || $download.length === 0)`
- `src/components/ms-download-queue.vue`（新增，104 行）+ `m-home-site.vue` 挂载
  - 复用 `ms-home-info.vue` 的 `.mansion-left`（`position:fixed; top:50%; left:0; transform:translateY(-50%)`）+ `el-card`
  - 宽屏卡片（暂停/继续/清空/重试 + 状态标签），窄屏降级为左下角 `el-tag` 徽标
  - 门控：`site instanceof Exhentai`

**关键设计决策**
1. 队列项**不持有闭包**，只存可序列化元数据（`gid/title/titleHash/index/dateMs`），执行时用已有 DOM id 重定位 → 干净可测、不污染 devtools
2. `success` 与 `skipped` 分开：`no-newer-seed` 时 `ok=true` 但 `downloaded=false`，标为「无更新」而非「已提交」（否则 UI 撒谎）
3. 面板文案用「已提交」而非「下载成功」—— `download()` 无回调，无法确认真正下载成功

**已知限制**（未修）
- `thunderDownload` / `copyUrl` 内部自带 `ElNotification`，`silent` 覆盖不到，队列跑 N 项仍弹 N 次原语通知
- 304 记录的 `date` 写入的是**种子日期**（`markAsNoNewerSeed`），而 `isNewer` 比的是**页面画廊日期**，口径不一致（既有问题）
- exhentai 未接入瀑布流（`mount()` 无 `waterfall.flow()`，`resolveElements()` 直接 throw），翻页整页刷新 → 队列不持久化，随页面清空

## 追加：304 去掉 `!isNewer` 判定

按用户要求，`exhentai.ts` 的 304 分支去掉了 `!isNewer` 门槛，改为**所有 304 条目一律置灰 + 入队**：

```ts
} else if (archive.status === HentaiArchiveStatus.NoNewerSeed) {
  // 304 一律置灰并加入下载队列自动复查下载页，不再比较画廊日期（仍允许手动点击）
  if ($download.length > 0) {
    ExhentaiUtils.applyArchiveStyle($download)
    queueDownload = true
  }
}
```

影响：
- 原先 304 + `isNewer`（画廊日期比归档新）的分支不再走"不置灰、直接绑定下载"，而是同样置灰并入队；手动点击仍可用（`data-mansion-lock` 保护）
- `isNewer` 现在只剩 200 分支使用，注释已同步改为「仅 200 比较画廊日期」
- 入队范围从"仅 !isNewer 的 304"扩大为"全部 304"，队列项数会明显增多（`intervalMs=1500` 下耗时相应变长）

验证：type-check ✓、build ✓（16.92s）、oxlint ✓。

## 追加：队列由串行改为并行（默认并发 2）

`src/store/download-queue-store.ts` 从"串行 + `busy` 守卫"改为"并发上限 + `workNumber` 计数"：

- state 新增 `limit: 2`（默认并发数）、`workNumber: number`；移除 `currentId` / `currentItem`（并发下"当前项"语义不成立）与单例 `timerHandle`
- `drain()`：`while (this.workNumber < this.limit)` 循环取 `pending` → 标 `running` → `workNumber++` → `void runOne(item)`。**循环体内无 await**，整个取任务过程同步完成，所以不会重复启动同一项
- 新增 `runOne(item)`：执行后 `finally` 里 `workNumber--`，再 `await sleep(intervalMs)`（**每个槽位各自**等一个间隔）然后重新 `drain()`
- 新增 `setLimit(n)` action（`Math.max(1, floor(n))`），调大后立即补位；未接 UI，仅程序可调
- `busy` 由 state 字段改为 **getter**（`workNumber > 0 || 有 pending`）
- `clear()` 只清 `items`，**不再重置 `workNumber`**、也不再 clearTimeout —— 因为清空计时器会让在途 `await sleep()` 的 Promise 永不 resolve 造成悬挂；而不重置 `workNumber` 才能保证并发上限不被绕过。`workNumber--` 加了 `Math.max(0, ...)` 兜底
- 面板 `visible` 从 `items.length > 0 || busy` 改为 `items.length > 0`（`busy` 变 getter 后，clear 完可能仍为 true 导致空面板）

验证：type-check ✓、oxlint ✓、eslint ✓、build ✓（17.68s）。
